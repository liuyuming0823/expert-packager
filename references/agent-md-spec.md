# Agent MD 规范

> 什么时候读：写 `agents/*.md` 正文时。这是专家的「人设 + 能力 + 流程」载体，写得好不好直接决定专家好不好用。

## 一、Frontmatter

```yaml
---
name: <agent-name>          # 必须与文件名一致，必须与 plugin.json 的 agentName 一致
description: <英文描述>      # 模型用它判断何时激活
displayName: { en: ..., zh: ... }
profession:  { en: ..., zh: ... }
maxTurns: 50                # 普通 Agent 50；主理人建议 150
---
```

**禁止声明 `tools` 字段**——所有工具权限由系统统一分配，写了也不会生效，还会被校验器判为不合规。

可选：`skills: [skill-name]` 声明启动时预加载的技能。

> 注意：**每个专家的 `agents/*.md` 都要自带完整 frontmatter**，这与插件包里普通 subagent 的写法一致。

## 二、正文结构

### 普通 Agent

```markdown
# {职业头衔} - {名字}

{一段话：这是谁、多少年经验、擅长什么、为谁服务}

## 核心能力
1. **{能力}**：{具体到什么粒度、用什么方法、产出什么}
2. ...
3. ...

## 工作流程
1. {接到需求先做什么——澄清什么、读什么}
2. {中间怎么推进}
3. {最后交付什么形态}

## 输出规范
- {格式要求}
- {语言与语气}
- {不确定项必须显式标注}

## 注意事项
- {边界：哪些不做}
- {数据真实性要求}
```

### 主理人（Team 型）

文件名必须带团队前缀（`my-team-team-lead.md`），`maxTurns` 建议 150-200。正文必须包含：

1. **团队成员表** —— 每个成员的 Agent ID、擅长领域（3-5 个具体能力点）、典型问法
2. **标准工作流程（SOP）** —— 分 Phase，每 Phase 写明「调度谁 / 输入从哪来 / 输出交给谁」
3. **团队协作机制（铁律）** —— 建团队 → 调度成员 → 消息中转 → 成员结论为准
4. **严禁行为清单** —— 禁止跳过建团队、禁止代写成员产出、禁止跳阶段、禁止成员直连、禁止 spawn 自己
5. **单 Agent 直调路由表** —— 单一维度问题直接调对应成员，综合问题走预设 Workflow

### 团队成员

- 不限制 tools
- 由主理人 spawn 为正式 teammate
- **必须写明：分析完成后通过 `SendMessage` 把结果回传给主理人**，不要直接回复用户

## 三、写作质量要求

| 要求 | 说明 |
|------|------|
| 能力要可执行 | 写「能做什么 + 用什么方法」，不写「非常专业」这类空话 |
| 流程要分步 | 每步说明输入与输出，让模型能照着走 |
| 输出要有模板 | 给出表格 / 分段骨架，避免每次产出形态漂移 |
| 边界要明确 | 写清不做什么，遇到越界需求怎么引导 |
| 数据要可核验 | 明确「只用可核验事实或用户提供的材料，禁止编造」 |
| 术语要保留 | 行业术语原样保留，不要为通俗而简化 |

## 四、能独立成一个 Agent 的标准

判据只有一条：**有没有用户会直接问它的问题？**

- 有 → 独立成一个 agent
- 没有 → 并进别的 agent

每个 agent 覆盖一个完整的「分析域」，域内多个能力可以归并，但不跨域。跨域协作交给主理人用 Workflow 编排。

## 五、大段资料怎么放

API 文档、字段表、知识库、长流程说明**不要塞进 Agent MD 正文**——正文会被完整读入上下文，塞多了会挤掉真正有用的信息。正确做法：

- 放 `skills/<skill-name>/references/`，由专家按需加载
- 或放专家包根目录的 `references/`，在 Agent MD 里写明「什么时候需要读它」
